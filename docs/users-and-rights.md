# Users, rights and authentication

[Documentation](README.md) · [Portal-NG](../README.md)

Portal-NG signs people in three ways, and they can all be enabled at once: **local accounts**, **LDAP /
Active Directory**, and **OpenID Connect**. Everything is configured in **Admin › Authentication**.

## Access rules

- **Administrators** — local super-admins, and members of a group flagged "Administrator" — have full
  access.
- A dashboard with **"All signed-in users"** visibility is visible to everyone signed in. Its access rules
  then only grant the right to edit.
- A dashboard with **"Restricted"** visibility is visible only to the listed groups and users.
- A rule targets a group (local, LDAP or OIDC) or a single user, with **View** or **View + edit**. A user
  gets the highest right among their own rules and their groups' rules.

Rights can be managed from three places, whichever matches the question you are asking:

| Where | What it shows |
|---|---|
| **Admin › Dashboards**, the access column | The visibility and rules of **one dashboard** |
| **Admin › Groups › Dashboards** | Every dashboard **one group** can view or edit |
| **Admin › Users › Dashboards** | A user's own rules, **and their effective access with the reason** (administrator, everyone, group X, a direct rule) |

That last one is the answer to "why does this person see this dashboard, or not".

### Granting rights before the first sign-in

LDAP and OIDC groups and accounts normally appear only after a synchronisation or a first sign-in. To
grant rights before that, declare them (Admin › Groups / Users › Declare…, or straight from the access
window by typing the exact identifier):

- **LDAP group**: its DN. **OIDC group**: the exact value in the groups claim — `/portal/staff` for a
  Keycloak group path, an object id for Entra ID.
- **LDAP account**: the value of the username attribute. **OIDC account**: the value of the username
  claim; the account is linked at its first sign-in.

Use a username claim that users **cannot change themselves** — not a self-editable `preferred_username`.

### Keeping groups in step

LDAP groups are refreshed at every sign-in and by the manual synchronisation. OIDC groups are refreshed at
every sign-in. Local groups assigned by hand are kept.

An LDAP group the synchronisation no longer finds is deleted — **except** when it carries dashboard rights
or the Administrator flag. It is then kept, without members, and reported, so that a wrong filter cannot
wipe out your rights. Delete it by hand if it is gone for good.

## LDAP / Active Directory

Admin › Authentication › LDAP. Presets for OpenLDAP, Active Directory and FreeIPA fill in the attribute
names; a **connection test** tells you what the directory answers before you save.

Configure the server URI (`ldaps://…`, or StartTLS), the bind account, the user base DN and filter, the
attributes for username, e-mail and display name, and the group base DN, filter and membership attribute.

- Filters are **escaped**; empty passwords are refused, so an empty password cannot become an anonymous
  bind that succeeds.
- A plaintext connection logs a warning.
- For LDAPS against an internal PKI, import the root CA in **Admin › Certificates** — see
  [Security](security.md#trusted-certificate-authorities).

## OpenID Connect

Admin › Authentication › OIDC. Authorization code flow with **PKCE S256**. Configure the issuer, the
client id and secret, the token authentication method, the scopes, the groups claim (nested claims are
supported) and the username claim.

The redirect URI is derived from `PUBLIC_URL`, so that must be the address users actually type.

- `state` is bound to the browser with a cookie, single-use, and valid for 10 minutes; `nonce` is checked.
- ID tokens are fetched directly from the provider over TLS and their signature is verified. `none` and
  `HS*` algorithms are refused.
- **Auto-redirect** sends users straight to the provider instead of showing the portal's own form.

OIDC accounts rely on the **provider's** multi-factor authentication; the portal's own two-step
verification does not apply to them.

## Two-step verification

Admin › Authentication › Two-step verification. It applies to **local and LDAP accounts**, and can be
**off**, **required for administrators**, or **required for everyone**.

Methods:

- **Authenticator apps (TOTP)** — the QR code is generated by the server, so no external service sees it.
  Codes are protected against replay and limited to 5 attempts per sign-in.
- **Security keys and passkeys (WebAuthn)** — bound to the portal's hostname, so `PUBLIC_URL` must match
  the address in the browser. Behind a proxy, that is the proxy's `https://` address.
- **Recovery codes** — 10 single-use codes per account.

Users manage their own methods from the user menu › **Security**. When verification is required, a user
without a method sets one up at their next sign-in, before getting access. An administrator can reset a
user's methods from Admin › Users (the shield button).

## Local sign-in and break-glass access

Local accounts, including the super-admin, can be prevented from signing in — Admin › Authentication ›
Local sign-in & sessions. This is only possible **while LDAP or OpenID Connect is enabled**, and if both
are later disabled, local sign-in comes back automatically.

If the directory or the SSO is unavailable, re-enable it from the compose file:

```yaml
# docker-compose.yml, backend service
FORCE_LOCAL_LOGIN: "true"
```

```bash
docker compose up -d backend    # recreates the backend with the variable
```

Sign in with the local super-admin, fix the configuration, then set the variable back to `false`. While it
is active, the administration shows a banner — it is not something to leave on by accident.

On Podman, the same switch is `Environment=FORCE_LOCAL_LOGIN=true` in `portal-ng-backend.container`; see
[Deployment](deployment.md#rootless-podman-quadlet).

## Protecting the sign-in itself

- Sessions: `HttpOnly`, `SameSite=Lax`, `Secure` behind HTTPS, with a configurable lifetime. A CSRF token
  is required on every state-changing request.
- Throttling: 10 failures per (IP, username) and 50 per IP over 15 minutes.
- Constant response time for unknown users, so the form cannot be used to find out who has an account.
- Local passwords are hashed with **Argon2id** (RFC 9106, 64 MiB, t=3, p=4) and rehashed automatically
  when the parameters change.
